## Motion-artwork research (2026-11-03)

- [Spotify Web API](https://developer.spotify.com/documentation/web-api) requires authorization and describes catalog metadata, search, and playback. Its track reference returns static album image URLs and explicitly requires visual content to remain unmodified and attributed with a link and Spotify logo. No Canvas-video endpoint is documented.
- [Apple Music API](https://developer.apple.com/documentation/applemusicapi) covers catalog metadata, and its [`Artwork` object](https://developer.apple.com/documentation/applemusicapi/artwork) describes an image URL. [Apple's motion-artwork guidance](https://itunespartner.apple.com/music/support/5499-create-deliver-motion-artwork) describes delivery through Transporter or a preferred provider; artist-page motion is restricted to direct partners. No public third-party motion-art retrieval API was found.
- [Deezer's official developer terms](https://cdn-content.dzcdn.net/pdf/CGU-developers.pdf) describe catalog API services including albums, artists, search, tracks, and users. The [developer API portal](https://developers.deezer.com/api) currently redirects to login, so current public access/app registration could not be verified. No documented animated-cover endpoint was found.
- [TIDAL's official API schema](https://tidal-music.github.io/tidal-api-reference/tidal-api-oas.json) documents artwork files and `mediaType` values `IMAGE`/`VIDEO`, including artist art relationships. This is a candidate for a future authenticated integration, not a verified Nuvx feature.

These are API capability findings, not completed Apple, Spotify, Deezer, or TIDAL integrations. The animated artwork currently implemented in Nuvx comes from community-submitted canvases.

## Music video and artist video status (2026-11-07)

- Video extraction uses the selected capable engine and optional fallback, with source validation before health success. The JVM/Android eXcor adapter maps separate picture/audio tracks from its public extractVideo API. InnerTubeX remains supported; video catalog search and artist pagination retain the primary catalog route.
- Shared video search, artist video shelves, conservative song matching, queue-preserving audio/video switching, and stream-address validation are implemented. Android routes through the existing MediaSession/Media3 player; desktop uses the existing VLC player and `input-slave` to pair sources. These are wired paths, not verified video playback.
- Artist video shelves now capture per-shelf continuation tokens and request additional catalog pages through InnerTubeX. The shared parser/router/UI tests cover page parsing, merges, duplicate videos, repeated tokens, empty pages, and use of the primary catalog backend; this does not verify playback.
- Live catalog validation now covers the shelf's public `moreContentButton` browse target and its nested `musicPlaylistShelfRenderer` continuation: the opt-in InnerTubeX route returned 100 videos followed by 16 more. Five artist results contained 10 populated video shelves and no initial continuation. This remains a renderer-based response shape rather than a typed upstream contract; the video-stream/GVS blocker below is unchanged.
- Song-to-video matching now rejects conflicting YouTube Music artist browse IDs when both results provide one, falls back to credited artist names when an ID is absent, and ranks explicit music-video title labels above lyric-video and visualizer labels. Duration remains the final tie-breaker; lyric/visualizer results can still be fallback candidates. Artist browse IDs and title text do not verify the uploading channel, so reliable official-channel classification is still incomplete.
- Historical Android smoke testing failed at stream resolution. The 2026-11-07 InnerTubeX v0.11.6 check still failed NO_PLAYABLE_STREAM/26 attempts; it does not establish the older PO-token diagnostic as the current cause. In contrast, live eXcor public-API and Nuvx selected-engine router checks resolved 1280x720 H264 with companion audio. These checks do not launch a native player or prove audible output.
- No private token/cookie workaround was added. The existing public eXcor API supplies the verified adaptive path. Progressive-only embedded-audio responses are rejected explicitly until the native source model supports them; mismatched audio/video headers or identity are rejected rather than silently changed.
- Desktop audio/video pairing uses VLC's `input-slave` option; VLC developers previously described that input feature as experimental ([VideoLAN developer discussion](https://mailman.videolan.org/pipermail/vlc-devel/2008-December/054177.html)). Current VLC runtime behavior remains unverified.
- Auto/Data saver/High requested-height caps reach video extraction. The eXcor adapter reports only the chosen observed height, not an invented list of available resolutions. Android mobile PiP is implemented for actively playing video, but entry/return and media controls remain unverified. Artist-page animated backgrounds, video-timed lyrics/captions, live-video behavior, video radio, and a native iOS player are not implemented. No video download flow is exposed without documented provider authorization.
